# 実装計画

## このドキュメントの目的

このドキュメントでは、業務用チャットアプリMVPを実装する順序を整理する。

`docs/01-purpose.md` から `docs/08-test-policy.md` までで整理した目的、ユーザー課題、スコープ、機能要件、データ設計、画面設計、技術構成、テスト方針をもとに、実装をどの順番で進めるかを明確にする。

新しい作業チャットで実装を依頼する場合は、このドキュメントと関連する `docs/` 配下の設計ドキュメントを確認してから進める。

## 実装順序の方針

このMVPでは、依存関係が強いものから順に実装する。

特に、以下の順序を基本とする。

```text
認証
  ↓
ユーザー・テナント作成
  ↓
権限制御
  ↓
チャンネル
  ↓
メッセージ
  ↓
テスト
  ↓
README整備
```

画面を先に作り込むよりも、認証、Firestore のデータ構造、ユーザー所属、テナント制御を先に固める。  
これにより、後続のチャンネル管理、メッセージ投稿、権限制御を実装しやすくする。

## Phase 1: データと認証の土台

Phase 1 では、画面を作り込む前に、アプリ全体の土台となる認証、型定義、Firestore 操作、ユーザー登録フローを実装する。

### 1. プロジェクト基盤の準備

実装すること:

- Next.js / TypeScript の初期設定を確認する
- Firebase SDK を導入・設定する
- Firebase Authentication と Firestore を利用できる状態にする
- 環境変数を整理する
- ディレクトリ構成を整理する
- ESLint、formatter、テストツールの設定を確認する

完了条件:

- アプリがローカルで起動できる
- Firebase 設定をアプリから参照できる
- TypeScript で実装を進められる
- テスト実行の前提が整っている

### 2. 型定義と共通ユーティリティ

実装すること:

- `UserRole` 型を定義する
- `AppUser` 型を定義する
- `Tenant` 型を定義する
- `Channel` 型を定義する
- `Message` 型を定義する
- 入力バリデーション関数を作成する
- 権限判定関数を作成する
- 日付表示用の関数を作成する

主な対象:

- メールアドレス形式チェック
- 必須入力チェック
- メッセージ本文の空文字・空白判定
- `admin` / `member` の判定
- チャンネル作成可否の判定
- Firestore 保存用データの生成

完了条件:

- データモデルに対応する型が定義されている
- 画面や Firestore 処理から共通利用できる関数が用意されている
- 単体テストを書きやすい構成になっている

### 3. Firebase Authentication 連携

実装すること:

- メールアドレスとパスワードによるユーザー登録
- メールアドレスとパスワードによるログイン
- ログアウト
- ログイン状態の取得
- 未ログインユーザーの認証後画面アクセス制御
- ログイン済みユーザーのログイン画面・登録画面アクセス制御

完了条件:

- Firebase Authentication でユーザー登録できる
- 登録済みユーザーがログインできる
- ログアウトできる
- 認証状態をアプリ側で参照できる
- 認証状態に応じて画面遷移を制御できる

### 4. Firestore データアクセス層

実装すること:

- `users/{userId}` の作成・取得
- `tenants/{tenantId}` の作成・取得
- `tenants/{tenantId}/channels/{channelId}` の作成・一覧取得
- `tenants/{tenantId}/channels/{channelId}/messages/{messageId}` の作成・一覧取得
- 画面から直接 Firestore を操作せず、データアクセス関数を経由する構成にする

主な対象:

- ログインユーザー情報取得
- 所属テナント情報取得
- 参加コードによるテナント検索
- チャンネル一覧取得
- メッセージ一覧取得

完了条件:

- Firestore の主要コレクションを操作できる
- データ取得・登録処理が関数として分離されている
- 後続の画面実装から再利用できる

### 5. ユーザー登録フロー

実装すること:

- 新規テナント作成によるユーザー登録
- 既存テナント参加によるユーザー登録
- 新規テナント作成時の `tenants/{tenantId}` 作成
- 登録ユーザーの `users/{userId}` 作成
- 新規テナント作成ユーザーを `admin` として保存する
- 既存テナント参加ユーザーを `member` として保存する
- 参加コード不正時のエラー処理

実装前に確認すること:

- 参加コード検索と Firestore Security Rules の整合性
- 参加コード不正時に Firebase Authentication のユーザーだけが残らない処理方針

MVPでの現実的な方針:

- Cloud Functions は初期MVPでは採用しない
- クライアントから参加コード検索を行う場合は、そのための Security Rules を明示的に設計する
- 参加コード検証後にアプリ用ユーザー情報を作成する
- 途中失敗時のエラー表示と後始末を実装する

完了条件:

- 新規テナント作成で管理者ユーザーとして登録できる
- 参加コードで既存テナントに一般ユーザーとして登録できる
- 登録後にチャンネル一覧画面へ遷移できる
- 不正な参加コードの場合にエラーを表示できる

## Phase 2: 主要画面、業務機能、権限制御

Phase 2 では、Phase 1 で作成した認証・データアクセスの土台を使い、ユーザーが操作する主要画面と業務機能を実装する。

この Phase では、画面上の表示制御だけでなく、Firestore Security Rules による基本的なデータアクセス制御も実装する。  
権限制御は画面、データ取得、データ登録と密接に関係するため、主要画面の実装と同じ Phase で扱う。

実装すること:

- 認証後画面の共通レイアウト
- アプリ名表示
- 所属テナント名表示
- ログインユーザー名表示
- ログアウトボタン

対象画面:

- チャンネル一覧画面
- チャンネル詳細画面
- テナント情報画面

完了条件:

- 認証後画面で共通情報が表示される
- どの認証後画面からでもログアウトできる

### 7. 認証画面

実装すること:

- `/signup`
- `/login`
- 入力バリデーション
- エラー表示
- ローディング表示
- 登録成功後の `/channels` 遷移
- ログイン成功後の `/channels` 遷移

完了条件:

- ユーザー登録画面から新規登録できる
- ログイン画面からログインできる
- 入力不備や認証失敗時にエラーを表示できる

### 8. チャンネル一覧画面

実装すること:

- `/channels`
- 所属テナント内のチャンネル一覧表示
- チャンネル名、チャンネル説明、作成日時の表示
- 管理者ユーザーのみチャンネル作成ボタンを表示
- チャンネル作成フォーム
- チャンネル名必須チェック
- 同一テナント内のチャンネル名重複チェック
- チャンネル詳細画面への遷移
- テナント情報画面への遷移

完了条件:

- 所属テナント内のチャンネル一覧を確認できる
- 管理者ユーザーはチャンネルを作成できる
- 一般ユーザーにはチャンネル作成ボタンが表示されない
- 作成したチャンネルが一覧に表示される

### 9. チャンネル詳細画面

実装すること:

- `/channels/[channelId]`
- チャンネル情報表示
- メッセージ一覧表示
- 投稿者名、投稿日時、本文の表示
- 投稿日時の昇順表示
- メッセージ投稿フォーム
- メッセージ本文必須チェック
- 空白のみのメッセージ投稿拒否
- 投稿後の入力欄クリア
- チャンネル一覧画面への戻るリンク

完了条件:

- チャンネル内のメッセージ一覧を確認できる
- メッセージを投稿できる
- 投稿したメッセージが一覧に表示される
- 投稿者名と投稿日時を確認できる

### 10. テナント情報画面

実装すること:

- `/tenant`
- テナント名表示
- ログインユーザー名表示
- メールアドレス表示
- ユーザー種別表示
- 管理者ユーザーのみ参加コード表示
- チャンネル一覧画面への戻るリンク

完了条件:

- 所属テナント情報を確認できる
- 自分のユーザー種別を確認できる
- 管理者ユーザーは参加コードを確認できる
- 一般ユーザーには参加コードが表示されない

### 11. Firestore Security Rules

実装すること:

- 未ログインユーザーの読み書き拒否
- ユーザー自身の `users/{userId}` 参照制御
- 所属テナントのテナント情報参照制御
- 所属テナント内のチャンネル参照制御
- 所属テナント内のメッセージ参照制御
- 管理者ユーザーのみチャンネル作成許可
- 所属テナント内のチャンネルのみメッセージ投稿許可
- 他テナントデータへのアクセス拒否

特に確認すること:

- 参加コード検索をどう許可するか
- 登録直後で `users/{userId}` が未作成のユーザーをどう扱うか
- 一般ユーザーが直接チャンネル作成処理を呼んでも拒否できるか

完了条件:

- 画面上の制御だけでなく、Firestore 側でも主要な権限制御が行われている
- 他テナントのデータにアクセスできない
- 一般ユーザーがチャンネルを作成できない

## Phase 3: 要件・設計の再確認、テスト、仕上げ

Phase 3 では、Phase 1 と Phase 2 で実装した内容をもとに、要件、設計、実装の整合性を再確認する。  
そのうえで、テストと README 整備を行う。

Firebase、Next.js、Firestore Security Rules は実装時の選択肢が多いため、主要機能が一通り動いた段階でベストプラクティスを確認し、必要に応じて設計や実装を調整する。

### 12. 要件・設計の再確認

実施すること:

- `docs/01-purpose.md` から `docs/09-implementation-plan.md` までを読み直す
- 実装済みの機能が MVP スコープから外れていないか確認する
- `docs/04-requirements.md` の機能要件と実装済み機能を照合する
- `docs/05-data-model.md` のデータ設計と Firestore 実装を照合する
- `docs/06-screens.md` の画面設計と実装済み画面を照合する
- `docs/07-tech-stack.md` の技術方針と実装方針を照合する
- `docs/08-test-policy.md` のテスト方針と実装予定のテストを照合する
- Firebase Authentication、Firestore、Firestore Security Rules、Next.js の実装方針を再確認する
- ベストプラクティスと大きくずれている箇所があれば修正方針を決める

特に確認すること:

- 参加コード検索と Firestore Security Rules の整合性
- 登録処理中に Firebase Authentication と Firestore の片方だけが成功した場合の扱い
- 認証状態の監視と画面遷移の実装方法
- Firestore の読み書きを画面から直接呼びすぎていないか
- 管理者ユーザーと一般ユーザーの権限判定が一箇所に集約されているか
- 他テナントデータへのアクセス拒否が画面制御だけに依存していないか

完了条件:

- 要件、データ設計、画面設計、実装内容の差分が把握できている
- 修正すべき設計・実装上の問題が整理されている
- テスト実装に入る前の前提が明確になっている

## 推奨する作業単位

実装は、以下の単位で作業チャットを分けると進めやすい。

| 作業単位 | 対象範囲 |
|---|---|
| Phase 1 | 1〜5: データと認証の土台 |
| Phase 2 | 6〜11: 主要画面、業務機能、権限制御 |
| Phase 3 | 12〜16: 要件・設計の再確認、テスト、仕上げ |

新しいチャットで Phase 1 を依頼する場合は、以下のように指示する。

```text
docs/09-implementation-plan.md を読んで、Phase 1「データと認証の土台」を実装して。
関連する docs 配下の設計も確認してから進めて。
```

## 完了条件

この実装計画は、以下を満たす状態で完了とする。

- MVP実装の順序が明確である
- 各 Phase の目的が明確である
- 各実装ステップの完了条件が明確である
- 新しい作業チャットでも実装範囲を理解できる
- `docs/01-purpose.md` から `docs/08-test-policy.md` までの設計と矛盾しない
