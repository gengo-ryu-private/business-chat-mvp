# 想定ユーザーと課題

## このドキュメントの目的

このドキュメントでは、業務用チャットアプリMVPの想定ユーザーと、そのユーザーが抱える課題を整理する。

このアプリでは、最初から機能を決めるのではなく、想定ユーザーの業務上の問題点を明確にしたうえで、MVPで解決する範囲を定義する。

## 想定する組織

このアプリは、小規模なチーム・組織で、口頭、メール、個人チャットなどを中心に業務連絡を行っている状態を想定する。

具体的には、以下のような組織を想定する。

- 小規模なWebサービス開発チーム
- 社内プロジェクトチーム
- 少人数の業務改善チーム
- 部署内の連絡チーム
- 業務委託や外部パートナーを含む小規模チーム

MVPでは、大企業向けの複雑な組織階層や高度な権限管理は扱わない。

## 現在の連絡手段

想定する組織では、主に以下のような手段で業務連絡を行っている。

- 口頭での連絡
- メール
- 個人チャット
- グループチャット
- 会議中の口頭共有
- 個人メモや共有メモ

これらの手段は手軽に使える一方で、業務上の情報を継続的に整理・共有するには課題がある。

## 現在の問題点

### 連絡内容が分散する

口頭、メール、個人チャットなど複数の手段で連絡していると、業務に関する情報が分散しやすい。

その結果、後から必要な情報を探すときに、どこで話された内容なのか分かりづらくなる。

### 過去のやり取りを確認しづらい

口頭で共有された内容や、個別のメール・チャットでやり取りされた内容は、後からチーム全体で確認しづらい。

特に、途中から参加したメンバーは、過去の経緯を把握しにくい。

### 話題ごとに情報を整理しづらい

すべての連絡が同じ場所で行われると、話題ごとの整理が難しくなる。

たとえば、以下のような内容が混在する可能性がある。

- 全体連絡
- 開発に関する相談
- 不具合報告
- 仕様確認
- 雑談や一時的な連絡

話題が混在すると、必要な情報を探す負担が大きくなる。

### 誰がいつ発言したか分かりづらい

口頭連絡や個別メッセージでは、誰がいつ何を共有したのかが残りにくい。

業務上の判断や確認を後から行う際に、発言者や時系列が分からないと、認識違いが起きやすくなる。

### 組織単位で情報を管理しづらい

個人のメールやチャットに情報が残っていると、組織として情報を管理しづらい。

担当者が変わった場合や、新しいメンバーが参加した場合に、必要な情報を引き継ぎにくくなる。

### 関係者以外への情報共有を避けたい

業務上の連絡には、関係者だけが確認できるべき情報が含まれる。

そのため、認証されたユーザーだけが、所属する組織の情報にアクセスできる必要がある。

## 解決したい課題

このMVPでは、上記の問題点に対して、以下の課題を解決することを目指す。

- 業務連絡をチーム内で一元管理できること
- 話題ごとに会話を整理できること
- 過去のやり取りを後から確認できること
- 誰がいつ発言したか分かること
- 組織単位でデータを分離できること
- 認証済みユーザーだけが利用できること

## このアプリの位置づけ

このアプリは、Slack や Chatwork などの既存チャットツールに機能面で勝つことを目的としたものではない。

小規模組織の情報共有課題を題材として、以下のような業務アプリケーションの基本構造を設計・実装することを目的とする。

- 認証
- テナント管理
- チャンネル管理
- メッセージ管理
- 権限制御
- テスト設計

そのため、MVPでは多機能なチャットツールを目指すのではなく、業務用アプリとして必要な基本構造を明確に実装することを重視する。

## 想定ユーザー

MVPでは、ユーザー種別を以下の2種類に分ける。

- 管理者ユーザー
- 一般ユーザー

## 管理者ユーザー

管理者ユーザーは、チーム用の利用環境を作成し、チャンネルを管理するユーザーである。

主な利用目的は以下の通り。

- チーム用のテナントを作成する
- 業務内容に応じてチャンネルを作成する
- チーム内の会話の場を整理する
- 参加コードを共有し、他のメンバーが参加できるようにする

MVPでは、管理者ユーザーはテナント作成者であり、チャンネル作成ができるユーザーとして扱う。

## 一般ユーザー

一般ユーザーは、作成済みのテナントに参加し、チャンネル内でメッセージを投稿・閲覧するユーザーである。

主な利用目的は以下の通り。

- 所属テナント内のチャンネルを確認する
- 業務連絡や相談をメッセージとして投稿する
- 他のユーザーの投稿を確認する
- チャンネルごとに会話内容を確認する

MVPでは、一般ユーザーはチャンネルの閲覧とメッセージ投稿を行うユーザーとして扱う。

## ユーザー種別と役割

| ユーザー種別   | 主な役割                           | MVPでできること                                    |
| -------------- | ---------------------------------- | -------------------------------------------------- |
| 管理者ユーザー | チーム用環境の作成とチャンネル管理 | テナント作成、チャンネル作成、メッセージ投稿・閲覧 |
| 一般ユーザー   | チャンネル内での情報共有           | チャンネル閲覧、メッセージ投稿・閲覧               |

## 利用シナリオ

### シナリオ1: 管理者がチーム用のチャット環境を作成する

1. 管理者ユーザーがアカウントを作成する
2. 管理者ユーザーが新しいテナントを作成する
3. 管理者ユーザーが業務内容に応じたチャンネルを作成する
4. 管理者ユーザーが参加コードをメンバーに共有する
5. チーム内でチャンネルを使った情報共有を開始する

このシナリオにより、チーム単位で情報共有の場を作成できることを確認する。

### シナリオ2: 一般ユーザーが既存テナントに参加する

1. 一般ユーザーがアカウントを作成する
2. 一般ユーザーが参加コードを入力する
3. 一般ユーザーが既存テナントに参加する
4. 所属テナント内のチャンネル一覧を確認する
5. 必要なチャンネルを選択する

このシナリオにより、既存チームにメンバーが参加できることを確認する。

### シナリオ3: ユーザーがチャンネル内でメッセージを投稿する

1. ユーザーがログインする
2. 所属テナントのチャンネル一覧を確認する
3. 利用したいチャンネルを選択する
4. メッセージを投稿する
5. 投稿されたメッセージを一覧で確認する

このシナリオにより、チーム内の情報共有がチャンネル単位で行えることを確認する。

### シナリオ4: チャンネルごとに会話を整理する

1. 管理者ユーザーが目的別にチャンネルを作成する
2. ユーザーが話題に合ったチャンネルを選択する
3. チャンネル内で関連するメッセージを投稿する
4. ユーザーがチャンネル単位で過去のやり取りを確認する

このシナリオにより、話題ごとに情報を整理できることを確認する。

## ユーザーストーリー

### 管理者ユーザー

- 管理者として、チーム用のテナントを作成したい。なぜなら、チーム単位で情報を管理したいから。
- 管理者として、業務内容ごとにチャンネルを作成したい。なぜなら、会話内容を整理しやすくしたいから。
- 管理者として、参加コードを確認したい。なぜなら、他のメンバーを既存テナントに参加させたいから。
- 管理者として、ログイン済みのユーザーだけが利用できる状態にしたい。なぜなら、業務情報を関係者以外に見られないようにしたいから。

### 一般ユーザー

- 一般ユーザーとして、既存テナントに参加したい。なぜなら、チームの情報共有に参加したいから。
- 一般ユーザーとして、自分が所属するテナントのチャンネルを確認したい。なぜなら、必要な業務連絡を探したいから。
- 一般ユーザーとして、チャンネル内にメッセージを投稿したい。なぜなら、チームメンバーに情報を共有したいから。
- 一般ユーザーとして、投稿者名と投稿日時を確認したい。なぜなら、誰がいつ発言した内容なのか把握したいから。

## MVPで重視すること

このMVPでは、ユーザー管理や権限管理を複雑にしすぎない。

初期段階では、以下を重視する。

- 認証済みユーザーだけが利用できること
- ユーザーがテナントに所属していること
- テナント単位でデータを分離できること
- チャンネル単位で会話を整理できること
- メッセージの投稿者と投稿日時が分かること

これにより、小規模組織の情報共有課題を題材に、業務用チャットアプリとして必要な基本構造を示す。
