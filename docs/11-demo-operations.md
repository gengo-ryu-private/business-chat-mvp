# 公開デモの運用手順

## 目的

デモ管理者がアカウントとデータを初期化、共有、点検、リセットするための手順を示す。
環境の構築は `docs/10-deployment-guide.md` で扱う。

## 運用方針

Firebase SparkとVercel Hobbyを使用する。
公開デモ専用のFirebaseに1つのデモテナントとadmin、memberを各1ユーザー用意し、
両方の認証情報を応募先へ個別共有する。
READMEやGitHubには認証情報と参加コードを載せない。

利用者によるmember、チャンネル、メッセージの追加は許容する。
ただし、初期データと追加データには実在する人物や企業の情報、個人情報、
機密情報、認証情報を入力しない。
新規テナント作成は停止し、signup APIのrate limitは有効にする。

## 初期デモデータ

| 種別       | 内容                                     |
| ---------- | ---------------------------------------- |
| テナント   | 架空の組織を1件                          |
| ユーザー   | 架空名のadminとmemberを各1件             |
| チャンネル | `お知らせ`、`雑談`など2〜3件             |
| メッセージ | 機能が分かる短い会話を各チャンネルに数件 |

固有のID、メールアドレス、パスワード、参加コードはドキュメントに記録せず、
アクセスを制限したパスワード管理手段で保管する。

## 初期化

1. Vercelが公開デモ専用Firebaseを参照していることを確認する。
2. 2つのテナント作成制限を一時的に `false` にして再デプロイする。
3. 公開画面でadminとテナントを作り、その参加コードでmemberを作る。
4. adminでチャンネルを作り、両ユーザーでメッセージを投稿する。
5. 2つのテナント作成制限を `true` に戻して再デプロイする。
6. テナント作成APIの403、両ユーザーのログイン、権限差、リアルタイム反映を確認する。

ここでいう2つの制限は、`DISABLE_PUBLIC_TENANT_SIGNUP` と
`NEXT_PUBLIC_DISABLE_TENANT_SIGNUP` を指す。
初期化中は公開URLの案内を停止する。

## 共有と点検

adminとmemberは常時ログイン可能にするが、認証情報は応募先だけに共有する。
adminではチャンネル作成と参加コードの確認、
memberでは一般ユーザーの権限制限を確認できる。

案内前と週1回を目安に、ログイン、初期デモデータ、権限、追加データの内容、
想定外のテナントの有無、各サービスの利用量を確認する。
通常のデモ操作による追加は残してよい。
選考終了時、表示が乱れたとき、不適切な内容や異常な利用量を確認したときにリセットする。

## リセット

Firestoreは親ドキュメントを削除してもサブコレクションを自動削除しない。
対象のFirebaseプロジェクト、テナントID、ユーザーUIDを確認し、次の順で削除する。

1. メッセージ
2. チャンネル
3. `users/{userId}`
4. `tenantSecrets/{tenantId}` と `tenants/{tenantId}`
5. Firebase Authenticationのadminとmember

削除後は初期化手順に従って初期デモデータを作り直し、古い認証情報を破棄する。
対象を判別できない場合は削除を続けない。

## 漏えい・異常時

認証情報の漏えいや異常な利用を確認した場合は案内を停止し、
デモユーザーのパスワードを変更する。
Admin SDK秘密鍵やUpstashトークンが関係する場合は失効・再発行して
Vercelを再デプロイする。
ログとデータを確認し、完全性を判断できなければリセットしてから共有を再開する。
