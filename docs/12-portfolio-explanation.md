# ポートフォリオ説明資料

## 目的

応募書類や面接で、本アプリの作成目的、設計、権限制御、技術選定を自分の言葉で説明するための要点を整理する。

本書は説明用の要約であり、要件や設計の正本は各項目から参照する既存ドキュメントとする。

## 作成目的

本アプリは、Webアプリケーションの要件定義、設計、実装、テスト、公開、運用までを一人で進められることを示すために開発した。

業務用チャットを題材にした理由は、メッセージの投稿・表示だけでなく、認証、組織単位のデータ分離、ユーザー権限、リアルタイム更新など、業務アプリに必要な設計と実装を含められるためである。画面の実装だけでなく、データ設計やセキュリティを考慮した開発能力を示す題材として適していると判断した。

## 想定ユーザーと解決する課題

専用のチャットツールを導入しておらず、口頭、メール、個人間のチャットなどで業務連絡を行っている小規模なチームを想定している。

連絡手段が分散していると、過去のやり取りや意思決定の経緯を確認しにくく、異なる話題が混在することで必要な情報を探しにくくなる。

本アプリでは、チャンネルごとに話題を分け、メッセージを時系列で保存する。これにより、情報の所在を分かりやすくし、途中から参加したメンバーでも過去の経緯を確認できるようにする。また、テナント単位でデータを分離し、組織内の情報を所属メンバーだけで共有できるようにする。

詳細は[想定ユーザーと課題](./01-users.md)を参照する。

## MVPの範囲

MVPは、想定ユーザーが組織へ参加し、話題ごとに継続的なコミュニケーションを取るために必要な機能へ絞った。

主な実装範囲は次のとおりである。

- ユーザー登録、ログイン、ログアウト
- 新規テナント作成、参加コードによる既存テナント参加
- チャンネルの作成、一覧・詳細表示
- メッセージの投稿、一覧表示、リアルタイム反映
- テナント単位のデータ分離
- `admin`と`member`による権限制御
- 主要ロジック、コンポーネント、利用フロー、Security Rulesのテスト

検索、通知、既読管理、ファイル添付などは利便性を高めるが、主要な課題を検証するための必須機能ではない。機能数を増やすよりも、主要機能の設計、権限制御、テスト、公開までを完成させることを優先し、今回のMVPから除外した。

詳細は[MVPスコープ](./02-scope.md)を参照する。

## データ設計

### 主要なコレクション

```text
users/{userId}
tenants/{tenantId}
tenantSecrets/{tenantId}
tenants/{tenantId}/channels/{channelId}
tenants/{tenantId}/channels/{channelId}/messages/{messageId}
```

各コレクションの役割は次のとおりである。

- `users/{userId}`: 表示名、メールアドレス、所属する`tenantId`、`role`、作成日時を保存する。ドキュメントIDと`id`にはFirebase AuthenticationのUIDを使用する
- `tenants/{tenantId}`: テナント名、作成者、作成日時を保存する
- `tenantSecrets/{tenantId}`: テナントへの参加コードを保存し、所属テナントの`admin`だけが参照できるようにする
- `tenants/{tenantId}/channels/{channelId}`: チャンネル名、説明、所属する`tenantId`、作成者、作成日時を保存する
- `tenants/{tenantId}/channels/{channelId}/messages/{messageId}`: メッセージ本文、投稿者、投稿日時、所属する`tenantId`と`channelId`を保存する

### usersをルートに配置する理由

ログイン直後に判明している識別子は、Firebase AuthenticationのUIDである。`users/{uid}`をルートに配置することで、UIDからユーザー情報を直接取得し、所属する`tenantId`と`role`を特定できる。

`tenants/{tenantId}/users/{userId}`のように配置すると、ユーザー情報を読む前に`tenantId`を知る必要が生じる。現在の「1ユーザーは1テナントに所属する」というMVPでは、UIDから直接取得できる構成を採用した。

### tenantIdの役割

`tenantId`は、ユーザー、チャンネル、メッセージがどのテナントに属するかを識別し、データを共有する範囲を制御するために使用する。

チャンネルとメッセージをテナント配下に配置することで、データの所属範囲をFirestoreのパス上でも明確にしている。ただし、配下に配置するだけではアクセス制御にはならない。Security Rulesで、ログインユーザーの`tenantId`とアクセス先の`tenantId`が一致することを検証する。

詳細は[データ設計](./04-data-model.md)を参照する。

## 認証と権限制御

### UID、tenantId、roleの役割

権限制御には、次の3つの値を使用する。

| 値         | 役割                                         |
| ---------- | -------------------------------------------- |
| UID        | ログインしているユーザー本人を識別する       |
| `tenantId` | ユーザーとデータが所属するテナントを識別する |
| `role`     | テナント内で許可する操作を判定する           |

Firebase Authenticationが「誰であるか」を認証し、FirestoreのユーザーデータとSecurity Rulesが「何を操作できるか」を判定する。

### adminとmemberの違い

`admin`には、所属テナントについて次の操作を許可する。

- テナント情報と参加コードの参照
- チャンネルの作成と参照
- メッセージの作成と参照

`member`には、次の操作を許可する。

- テナント情報の参照
- チャンネルの参照
- メッセージの作成と参照

`member`には、参加コードの参照とチャンネルの作成を許可しない。

`admin`にも、ユーザーやテナントの更新・削除、チャンネルやメッセージの更新・削除は許可していない。これらは今回のMVPの対象外である。

### 画面とSecurity Rulesの二重の制御

画面では、`member`にチャンネル作成フォームを表示しないなど、ユーザーに不要な操作を提示しないための制御を行う。

ただし、ブラウザ側の制御は、開発者ツールからFirebase Client SDKを直接呼び出したり、リクエストを改変したりすることで回避される可能性がある。そのため、Security Rulesを最終的な認可境界とし、データベースの直前でも不正な操作を拒否する。

### 登録処理をサーバー側で行う理由

新規テナント作成と既存テナント参加は、Next.js Route HandlerとFirebase Admin SDKで処理する。

サーバー側で決定または生成する主な値は次のとおりである。

- Firebase AuthenticationのユーザーID
- `tenantId`
- `role`
- 新規テナントの参加コード
- `createdBy`
- 作成日時と更新日時

新規テナントを作成したユーザーの`role`は`admin`に固定し、参加コードで既存テナントへ参加したユーザーは`member`に固定する。

これらをブラウザ側で決定させると、リクエストを改変して自分を`admin`として登録したり、本来とは異なるテナントへ所属したりする可能性がある。そのため、ブラウザから受け取る入力を検証し、所属先と権限はサーバー側で決定する。

Firebase Admin SDKはSecurity Rulesを経由しないため、Route Handler側で入力検証、権限情報の決定、失敗時の後始末を行う。

### 参加コードを分離する理由と制約

Firestoreでは、1つのドキュメントを読み取らせながら、特定のフィールドだけをユーザー種別によって非表示にできない。そのため、全メンバーが参照する`tenants`と、`admin`だけが参照する`tenantSecrets`を分離している。

この設計は、参加後の`member`による参加コードの再確認や、通常のテナント情報取得によるコードの露出を防ぐ。一方、参加コードをすでに知っているユーザーによる第三者への再共有は防げない。

より厳密な参加管理が必要な場合は、コードの失効・有効期限、1回限りの招待トークン、`admin`による参加承認などが改善案となる。

詳細は[データ処理フロー](./05-data-flow.md)と[Firestore Security Rules](../firestore.rules)を参照する。

## 技術選定

### Next.js

Reactによる画面、ルーティング、登録処理に必要なサーバーAPIを、1つのTypeScriptプロジェクトで実装するために採用した。

本アプリの登録処理では、認証ユーザーの作成、テナントの作成・検索、参加コードの生成・照合、`tenantId`と`role`の決定を一連の処理として行う。Route Handlerを使用することで、ブラウザからは必要な入力だけを受け取り、所属先と権限を信頼できるサーバー側で決定できる。

フロントエンドとサーバー処理を同じリポジトリで管理でき、Vercelへ画面とRoute Handlerをまとめてデプロイできる点も、一人でMVPを開発・公開する目的に適している。

一方、ブラウザ用コードとサーバー専用コードの責務を明確に分ける必要がある。また、Route Handlerを使用するため、静的ファイルだけを配信するホスティングでは動作しない。

### TypeScript

ユーザー、テナント、チャンネル、メッセージなどのデータ構造と、関数やコンポーネントの入出力を型で定義するために採用した。

必須フィールドの不足や型の不一致を実行前に検出でき、データ構造を変更したときの影響範囲も把握しやすくなる。フロントエンドとRoute Handlerを同じ言語で実装できる点も、一人で開発・保守するうえでの利点である。

ただし、TypeScriptの型は実行時には存在しない。外部から受け取るリクエストの安全性は保証できないため、登録APIではZodによる実行時検証も行う。

### Firebase Authentication

メールアドレスとパスワードによるユーザー登録、ログイン、ログアウトと、ログインユーザーの識別に使用する。

認証を独自実装すると、パスワードの安全な保管、認証トークンの発行・検証、ログイン状態の維持などを安全に構築する必要がある。認証基盤をFirebaseに任せることで、独自実装によるセキュリティリスクと開発負担を抑え、テナント管理や権限制御などのアプリ固有の機能に注力できる。

Firebase AuthenticationのUIDを`users/{uid}`と対応させ、Security Rulesの`request.auth.uid`からログインユーザーの`tenantId`と`role`を参照できる点も採用理由である。

一方、Firebaseの仕様、利用上限、料金体系に依存する。`tenantId`や`role`などのアプリ固有の権限情報は、Firestoreで別途管理する必要がある。

### Cloud Firestore

ユーザー、テナント、参加コード、チャンネル、メッセージを保存するデータベースとして採用した。

主な採用理由は、チャットに必要なリアルタイム更新と、Firebase Authentication、Security Rulesを組み合わせたテナント単位のアクセス制御を、比較的少ない実装で実現できることである。

チャンネル内のメッセージは`onSnapshot`でリアルタイム購読する。これにより、新しい投稿を画面の再読み込みなしで反映でき、WebSocketサーバーなどを独自に構築する必要がない。

RDBではなくFirestoreを選んだのは、今回のMVPでは複雑な結合や集計よりも、リアルタイム更新、階層的なデータ管理、Firebase Authenticationとの連携、開発・運用負担の小ささを優先したためである。

一方、複雑なリレーションや集計、一意制約はRDBのほうが扱いやすい。現在はチャンネル名の一意性をブラウザ側で確認しているため、同時作成による重複までは保証できない。データ量が増えた場合は、ページネーションや読み取り回数を考慮した設計も必要になる。

### Firebase Admin SDK

Route HandlerからFirebase AuthenticationとFirestoreを管理者権限で操作し、登録処理を安全に実行するために採用した。

登録処理では、認証ユーザーの作成、参加コードによるテナント検索、新規テナントと参加コードの作成、`tenantId`と`role`の決定、ユーザーデータの作成、失敗時の後始末が必要になる。これらをサーバー側へ集約することで、権限の根拠をブラウザからの自己申告に依存させない。

一方、ログイン後の通常操作ではFirebase Client SDKを使用し、Security Rulesでアクセスを制御する。

```text
登録処理
Route Handler → Firebase Admin SDK
  └─ tenantIdとroleをサーバー側で決定する

ログイン後の通常操作
ブラウザ → Firebase Client SDK → Security Rules → Firestore
  └─ 所属テナントとroleに基づいて許可を判定する
```

Admin SDKはSecurity Rulesを経由しないため、Route Handlerで入力値と操作対象を検証し、認証情報をブラウザへ公開しないことが重要である。

### Firestore Security Rules

Firebase Client SDKからFirestoreへ直接アクセスするログイン後の操作について、データベースの直前でテナント分離、権限制御、データ検証を行うために採用した。

Security Rulesでは、主に次を確認する。

- Firebase Authenticationでログインしているか
- アクセス先がユーザーの所属テナントか
- チャンネル作成者が`admin`か
- メッセージの投稿者がログインユーザー本人か
- 許可されたフィールドだけが含まれているか
- 文字数や作成日時が要件を満たしているか

すべての操作をサーバーAPI経由にすると、チャンネルやメッセージの取得・作成、リアルタイム配信について個別にAPIを実装する必要がある。Security Rulesを認可境界にすることで、Client SDKの取得・作成とリアルタイム購読を利用しながら、不正なアクセスをFirestore側で拒否できる。

Firebase Authenticationは「誰がログインしているか」を確認する認証を担当し、Security Rulesは「そのユーザーに操作を許可するか」という認可と、書き込むデータの検証を担当する。

一方、Security Rulesは、複雑な業務処理、フィールド単位の参照制御、一意制約には向いていない。また、Admin SDKからの操作には適用されない。Rulesの記述ミスがアクセス制御の不具合につながるため、Firebase Emulatorを使用してRules自体も自動テストしている。

詳細は[技術構成](./07-tech-stack.md)と[テスト方針](./08-test-policy.md)を参照する。

### React

画面を役割ごとのコンポーネントへ分割し、表示や状態管理の責務を整理するために採用した。

ログインフォーム、チャンネル一覧、チャンネル作成フォーム、メッセージ一覧、投稿フォームなどを個別のコンポーネントにすることで、再利用しやすく、変更時の影響範囲を限定できる。

一方、コンポーネントを細かく分けすぎると、データや関数の受け渡しが複雑になる。画面上の役割を基準に、適切な単位で分割する必要がある。

### Tailwind CSS

ユーティリティクラスを組み合わせてスタイルを指定し、独自CSSクラスの命名と管理を減らすために採用した。

スタイルが適用される要素と指定内容を同じ場所で確認でき、小規模なMVPを効率的に実装しやすい。一方、指定が増えると`className`が長くなるため、繰り返すUIはコンポーネントとして共通化する必要がある。

### shadcn/ui

ボタン、入力欄、カード、アラートなどの基本的なUIを、統一された見た目と操作性で実装するために採用した。

コンポーネントのソースコードをプロジェクト内で管理できるため、既製のUIを利用しながら、必要に応じて挙動やデザインを変更できる。今回のMVPでは独自性の高いデザインよりも、業務アプリとして必要な画面を一定の品質で、少ない工数で実装することを優先した。

### Zod

ブラウザとRoute Handlerで共通のスキーマを使用し、入力条件の不一致を防ぐために採用した。

ブラウザ側の検証は、送信前にエラーを表示して操作性を高める役割を持つ。一方、ブラウザ側の処理は回避できるため、Route Handlerでも同じスキーマを使って再検証する。

TypeScriptの型は実行時には存在せず、外部から送られた値が型どおりであることを保証できない。そのため、Zodによる実行時検証を組み合わせている。

### テスト技術の使い分け

テスト対象の範囲とリスクに応じて複数の手段を使い分け、単体処理から実際の利用フローまで段階的に確認する。

#### Vitest

Firebaseや画面表示に依存しない処理を短時間で確認するために使用する。入力検証、権限判定、参加コード生成、Firestore保存用データの生成、signup API、rate limitなどが主な対象である。

#### React Testing Library

コンポーネントをユーザー操作に近い形で確認するために使用する。フォームの入力、エラー表示、`role`による表示の違い、送信内容などを確認する。Firebaseとの通信はモックし、コンポーネントの責務に限定してテストする。

#### Playwright

複数の画面と機能にまたがる主要な利用フローを、実際のブラウザ上で確認するために使用する。`admin`によるテナントとチャンネルの作成、`member`の参加、メッセージ投稿、リアルタイム反映、ログアウト後のアクセス制御までを一連の流れとして確認する。

#### Firebase Emulator

本番Firebaseを変更せずに、AuthenticationとFirestoreを使用するテスト環境を構築するために使用する。Security Rulesの許可・拒否、PlaywrightによるE2E、デモテナント運用CLIのライフサイクルを確認する。

### Vercel

Next.jsの画面とRoute Handlerを、少ない構築手順で同じ環境へデプロイするために採用した。

Next.jsのサーバー処理を実行でき、GitHubと連携したデプロイや環境変数の管理も行えるため、一人で公開・更新する今回のMVPに適している。

一方、実行環境や料金体系がVercelへ依存するため、利用量とサーバー処理の実行回数を確認しながら運用する必要がある。

### Upstash Redis

公開されたsignup APIに、IPアドレス単位のrate limitを適用するために採用した。

Vercelのサーバー処理は、複数のインスタンスで実行されたり再起動されたりする可能性がある。サーバーのメモリ内で回数を管理するのではなく、複数の実行環境から共有できる外部ストレージが必要になる。Upstash RedisはREST API経由で利用でき、Vercel上のRoute Handlerから扱いやすいと判断した。

本アプリはRedis障害時に登録処理を継続する設計である。そのため、rate limitだけに依存せず、公開デモでは新規テナント作成自体もサーバー側で無効化している。

詳細は[公開デモのデプロイガイド](./10-deployment-guide.md)を参照する。

## CODEXの利用と自分の判断

CODEXを、意思決定を代行するものではなく、選択肢と判断材料を増やし、実装とレビューを支援するための道具として使用した。

### CODEXに任せた部分

- 要件を実現するための選択肢と判断材料の提示
- 指示した要件に基づくコードとドキュメントの下書き
- テストケースや考慮漏れの候補出し
- コードレビュー結果を受けた修正
- 実装とドキュメントの整合性確認

### 自分で判断した部分

- アプリの作成目的と想定ユーザー
- MVPへ含める機能と除外する機能
- セキュリティや公開デモに必要な制約
- 提示された選択肢の採用、修正、却下
- コード、テスト、ドキュメントのレビュー
- 最終的な仕様と完了条件

### 判断例1: 登録処理のサーバー集約

ユーザー登録では、`tenantId`と`role`をどこで決定するかがセキュリティ上の課題となった。

CODEXを使ってクライアント処理とサーバー処理の選択肢やリスクを整理し、権限の根拠をブラウザからの自己申告に依存させないことを重視した。その結果、登録処理をNext.js Route HandlerとFirebase Admin SDKへ集約する方針を採用した。

ブラウザから受け取る入力はZodで再検証し、`tenantId`と`role`はサーバー側で決定する。また、処理途中で失敗した場合は、作成済みの認証ユーザーやテナントを削除する設計とした。

この例では、CODEXに選択肢とリスクの整理、コードとテストの下書きを任せ、セキュリティ上の優先条件、採用する構成、完了条件を自分で判断した。

### 判断例2: 公開デモの制限

完成したアプリを、誰でも新規テナントを作成できる状態で公開すると、不正利用、データ管理、利用量増加のリスクがある。

CODEXを使ってrate limitや公開方法の選択肢を整理したうえで、rate limitだけに依存せず、公開環境では新規テナント作成を無効化する方針を採用した。応募先には共通環境を公開せず、応募先ごとに分離したデモテナントとアカウントをCLIで発行する。

この例では、CODEXに対策案、トレードオフ、実装と運用手順の下書きを任せ、許容する公開リスク、応募先ごとのデータ分離、認証情報の共有範囲、運用方針を自分で判断した。

詳細は[公開デモの運用手順](./11-demo-operations.md)を参照する。

## MVPの制約と発展可能性

### 判断方針

現在のMVPには、想定ユーザーが組織へ参加し、チャンネルごとにメッセージを共有するための主要機能を実装している。一方、短期間で要件定義から公開・運用までを完成させるため、セキュリティの拡張、データ増加への対応、高度なチャット機能の一部を対象外とした。

実運用規模へ拡張する場合は、機能数を増やすことよりも、次の順序で検討する。

1. セキュリティとデータ保護に関係する問題
2. データの整合性や主要機能の信頼性に関係する問題
3. ユーザー数やデータ量の増加によって発生する問題
4. 想定ユーザーの主要課題をさらに解決する機能
5. 利便性を高める追加機能
6. 複数テナント所属など、MVPの前提を広げる組織・アカウント管理

### 現在の制約

#### 参加・権限管理

- 参加コードを知っているユーザーによる第三者への再共有を防げない
- 参加コードの失効、再発行、有効期限を実装していない
- `admin`による参加承認を実装していない
- 複数`admin`、`role`の変更、ユーザー削除に対応していない
- 1ユーザーが複数テナントへ所属する構成に対応していない

現在のMVPでは、参加コードによって既存テナントへ参加できることと、`admin`と`member`の基本的な権限差を検証することを優先した。厳密な招待管理と組織管理は、権限モデルと管理画面の範囲が広がるため対象外とした。

#### データ整合性

- チャンネル名の一意性をブラウザ側で確認しているため、同時作成による重複までは保証できない
- チャンネルとメッセージの編集・削除を実装していない
- 削除時の関連データ、権限、監査記録に関する設計がない

現在のMVPでは、新しいチャンネルを作成し、メッセージを継続的に投稿・参照する流れを優先した。編集・削除を追加すると、誰が変更できるか、履歴を残すか、関連データをどう扱うかまで決める必要があるため対象外とした。

#### 性能と拡張性

- チャンネル内のメッセージを全件リアルタイム購読している
- メッセージのページネーションと過去データの追加読み込みを実装していない
- 大量データ、同時接続、負荷、Firestoreの読み取り量を検証していない
- メッセージ検索に対応していない

現在のMVPでは、少人数のチームでメッセージがリアルタイムに共有されることの検証を優先した。大量データを前提とする取得方法や検索基盤は、MVPの想定規模を超えるため対象外とした。

#### 認証とアカウント管理

- メールアドレス確認、パスワード再設定、多要素認証を実装していない
- ユーザー自身によるプロフィール変更やアカウント削除を実装していない

現在のMVPでは、メールアドレスとパスワードによる基本的な登録、ログイン、ログアウトと、認証状態に基づくアクセス制御を優先した。

#### チャットの利便性

- 通知、既読管理、メンション、リアクションを実装していない
- ファイル・画像の添付、スレッド、ダイレクトメッセージを実装していない

これらはチャットの利便性を高めるが、チャンネルごとに情報を保存・共有するという主要課題の検証には必須ではないため、MVPから除外した。

#### 公開・運用

- 公開デモのテナント発行、点検、リセット、削除にはローカルCLIの操作が必要である
- 管理画面、監査ログ、障害の自動通知を実装していない
- rate limit用のRedisに障害が発生した場合は、登録処理を継続する構成である

公開デモでは、rate limitだけに依存せず、新規テナント作成をサーバー側でも無効化する。応募先ごとに分離したデモテナントを発行し、共有範囲と削除時期を管理することで、現在の運用上の制約を補っている。

### 実運用へ拡張する場合の検討順序

#### 検討順序1: 参加・権限管理の強化

参加コードの失効・再発行、有効期限、1回限りの招待、または`admin`による参加承認を検討する。あわせて、複数`admin`と`role`変更の要件を整理する。

現在の参加コード方式では、コードを知っているユーザーによる再共有を防げず、`admin`が参加者を完全には管理できない。テナント内データの公開範囲に関係するため、機能追加より先に検討する。

#### 検討順序2: データ整合性の強化

チャンネル名の一意性を、同時作成を含めて保証できる方法へ変更する。編集・削除を追加する場合は、操作権限、履歴、関連するメッセージの扱いを先に定義する。

利用者が増えた場合にも一貫したデータを維持し、後から管理機能を追加できる状態にすることを目的とする。

#### 検討順序3: メッセージ取得の拡張性

メッセージの取得件数を制限し、ページネーションと過去メッセージの追加読み込みを実装する。想定データ量を決め、表示速度、リアルタイム購読範囲、Firestoreの読み取り量を検証する。

現在はメッセージを全件購読するため、データの増加が表示速度と利用量に影響する可能性がある。検索などの機能を追加する前に、基本となる取得方法の改善を検討する。

#### 検討順序4: メッセージ検索

チャンネル、投稿者、期間、キーワードによる検索方法を検討する。Firestoreだけで実現する範囲と、外部検索サービスを使用する場合のデータ同期、権限制御、運用負担を比較する。

検索は「過去の経緯を確認しやすくする」という主要課題に直接関係する。ただし、データ量の増加を前提とするため、メッセージ取得の拡張性を整えた後の検討対象とする。

#### 検討順序5: チャットの利便性向上

通知、既読管理、メンション、ファイル添付、リアクションなどを、想定ユーザーの必要性に基づいて選定する。

これらは利用体験を高める一方、現在のMVPでも基本的なコミュニケーションは可能である。そのため、セキュリティ、拡張性、データ整合性、検索より後の検討対象とする。

#### 検討順序6: 組織・アカウント管理の拡張

1ユーザーが複数テナントへ所属できる構成など、現在のMVPで固定している組織・アカウント管理の前提を見直す。

データモデル、権限判定、画面遷移への影響が大きいため、現在の単一テナント構成における安全性、整合性、拡張性を整えた後に検討する。

### 面接での説明例

> 本アプリは、要件定義から公開環境の運用までを検証するMVPとして完成しています。実運用規模へ拡張する場合は、まず参加コードの再共有を防げないという権限制御上の制約、次にチャンネル名の一意性などのデータ整合性と、メッセージ取得のページネーションを検討します。その後の候補として、メッセージ検索、通知や既読管理などの利便性向上、複数テナント所属などの組織・アカウント管理の拡張があります。
