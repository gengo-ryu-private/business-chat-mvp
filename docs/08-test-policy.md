# テスト方針

## このドキュメントの目的

このドキュメントでは、業務用チャットアプリMVPにおけるテスト方針を整理する。

`docs/02-users.md` では、小規模組織における業務連絡の課題を整理した。  
`docs/03-scope.md` では、その課題に対してMVPで対応する範囲を定義した。  
`docs/04-requirements.md` では、MVPで実装する機能要件を整理した。  
`docs/05-data-model.md` では、Firestore を前提としたデータ構造を整理した。  
`docs/06-screens.md` では、ユーザーが操作する画面を整理した。  
`docs/07-tech-stack.md` では、採用技術とその役割を整理した。

このドキュメントでは、それらの要件を満たすために、何をどの粒度でテストするかを明確にする。

## テスト方針

このMVPでは、すべてを網羅的にテストすることよりも、主要な機能が意図通り動作することを確認できる状態を目指す。

特に、以下を重視する。

- 主要なロジックが正しく動作すること
- 入力値のバリデーションが正しく動作すること
- ユーザー種別による表示制御が正しく動作すること
- 認証状態に応じた画面制御が行われること
- 所属テナントに応じたデータ制御が行われること
- ユーザー登録、ログイン、チャンネル作成、メッセージ投稿の基本操作が通ること
- 新しいメッセージが画面更新なしで一覧に反映されること
- エラー時に適切なメッセージが表示されること

## 使用するテストツール

| テスト種別           | 使用ツール            | 主な対象                                     |
| -------------------- | --------------------- | -------------------------------------------- |
| 単体テスト           | Vitest                | バリデーション、権限判定、データ整形処理     |
| コンポーネントテスト | React Testing Library | フォーム、一覧、表示制御、エラー表示         |
| E2Eテスト            | Playwright            | ユーザー登録からメッセージ投稿までの主要操作 |

## テスト対象の考え方

MVPでは、以下の観点でテスト対象を選ぶ。

- ユーザーの主要操作に関わること
- 業務用アプリとして重要な認証・権限制御に関わること
- 入力ミスや権限エラーなど、ユーザーが遭遇しやすいこと
- 実装ミスが起きやすいロジックであること
- ポートフォリオとして品質意識を示しやすいこと

一方で、Firebase Authentication や Firestore 自体の内部挙動は、テスト対象としない。

## 1. 認証機能のテスト

### 対象

- ユーザー登録フォーム
- ログインフォーム
- ログアウト処理
- 未ログイン時の画面制御
- ログイン済みユーザーの画面制御

### 確認すること

- ユーザー名が未入力の場合、エラーが表示される
- メールアドレスが未入力の場合、エラーが表示される
- メールアドレス形式が不正な場合、エラーが表示される
- パスワードが未入力の場合、エラーが表示される
- ログイン成功時にチャンネル一覧画面へ遷移する
- ログアウト後にログイン画面へ遷移する
- 未ログインユーザーは認証後の画面にアクセスできない
- ログイン済みユーザーがログイン画面へアクセスした場合、チャンネル一覧画面へ遷移する

## 2. テナント管理機能のテスト

### 対象

- 新規テナント作成
- 参加コードによる既存テナント参加
- 所属テナント情報の表示
- 参加コードの表示制御

### 確認すること

- 新規テナント作成時に、ユーザーが管理者として登録される
- 新規テナント作成時に、テナント情報が作成される
- 参加コードを使って既存テナントに参加できる
- 不正な参加コードの場合、エラーが表示される
- ログインユーザーの所属テナント情報が表示される
- 管理者ユーザーには参加コードが表示される
- 一般ユーザーには参加コードが表示されない

## 3. チャンネル管理機能のテスト

### 対象

- チャンネル作成フォーム
- チャンネル一覧表示
- チャンネル詳細画面への遷移
- 管理者ユーザーと一般ユーザーの表示制御

### 確認すること

- 管理者ユーザーはチャンネル作成ボタンを表示される
- 一般ユーザーはチャンネル作成ボタンを表示されない
- 管理者ユーザーはチャンネルを作成できる
- 一般ユーザーはチャンネルを作成できない
- チャンネル名が未入力の場合、エラーが表示される
- 同一テナント内でチャンネル名が重複する場合、エラーが表示される
- 作成したチャンネルが一覧に表示される
- チャンネルを選択すると詳細画面へ遷移する

## 4. メッセージ機能のテスト

### 対象

- メッセージ投稿フォーム
- メッセージ一覧表示
- 投稿者名と投稿日時の表示
- メッセージ本文のバリデーション

### 確認すること

- メッセージを投稿できる
- 空のメッセージは投稿できない
- 空白のみのメッセージは投稿できない
- 投稿したメッセージが一覧に表示される
- メッセージに投稿者名が表示される
- メッセージに投稿日時が表示される
- メッセージ本文が表示される
- メッセージは投稿日時の昇順で表示される
- 他ユーザーの新しい投稿がメッセージ一覧に自動表示される
- 投稿成功後、入力欄が空になる

## 5. 権限制御のテスト

### 対象

- 認証状態による画面アクセス制御
- 管理者ユーザーの操作
- 一般ユーザーの操作
- テナント外データへのアクセス制御

### 確認すること

- 未ログインユーザーはチャンネル一覧画面にアクセスできない
- 未ログインユーザーはチャンネル詳細画面にアクセスできない
- 未ログインユーザーはテナント情報画面にアクセスできない
- 管理者ユーザーだけがチャンネルを作成できる
- 一般ユーザーはチャンネルを作成できない
- ユーザーは所属テナント内のチャンネルだけを閲覧できる
- ユーザーは所属テナント内のメッセージだけを閲覧できる
- ユーザーは所属テナント内のチャンネルにだけメッセージを投稿できる
- ユーザーは他テナントのデータを閲覧できない

## 単体テスト

単体テストでは、画面に依存しないロジックを中心に確認する。

### 使用ツール

- Vitest

### 主な対象

- 入力値のバリデーション
- メールアドレス形式チェック
- メッセージ本文の空文字・空白判定
- ユーザー種別の判定
- チャンネル作成可否の判定
- 参加コード入力チェック
- Firestore保存用データの生成
- 表示用の日付変換

### テスト例

| 対象                         | 確認内容                                   |
| ---------------------------- | ------------------------------------------ |
| メールアドレスバリデーション | 正しいメール形式のみ許可される             |
| 必須入力チェック             | 空文字の場合にエラーが返る                 |
| メッセージ本文バリデーション | 空文字・空白のみを拒否する                 |
| 権限判定                     | `admin` のみチャンネル作成可能と判定される |
| 参加コードチェック           | 参加コード未入力の場合にエラーが返る       |
| 日付変換                     | 投稿日時を画面表示用に変換できる           |
| Firestoreデータ生成          | 保存に必要なフィールドが含まれる           |

## コンポーネントテスト

コンポーネントテストでは、ユーザー操作に近い形で画面部品の表示・操作を確認する。

### 使用ツール

- React Testing Library

### 主な対象

- ログインフォーム
- ユーザー登録フォーム
- チャンネル作成フォーム
- チャンネル一覧
- メッセージ投稿フォーム
- メッセージ一覧
- テナント情報表示
- 共通レイアウト

### テスト例

| 対象                   | 確認内容                                           |
| ---------------------- | -------------------------------------------------- |
| ログインフォーム       | メールアドレスとパスワードを入力できる             |
| ログインフォーム       | 未入力時にエラーが表示される                       |
| ユーザー登録フォーム   | 登録方法によって入力欄が切り替わる                 |
| ユーザー登録フォーム   | 新規テナント作成時にテナント名入力欄が表示される   |
| ユーザー登録フォーム   | 既存テナント参加時に参加コード入力欄が表示される   |
| チャンネル作成フォーム | チャンネル名未入力時にエラーが表示される           |
| チャンネル一覧         | 渡されたチャンネル情報が表示される                 |
| チャンネル一覧         | 一般ユーザーにはチャンネル作成ボタンが表示されない |
| メッセージ投稿フォーム | 入力後に投稿ボタンを押せる                         |
| メッセージ投稿フォーム | 空白のみの場合にエラーが表示される                 |
| メッセージ一覧         | 投稿者名・日時・本文が表示される                   |
| メッセージ一覧         | 新しい投稿が渡されたときに一覧表示へ反映される     |
| テナント情報表示       | 管理者のみ参加コードが表示される                   |

## E2Eテスト

E2Eテストでは、ユーザーが実際にアプリを操作する流れを確認する。

### 使用ツール

- Playwright

### 主な対象シナリオ

## シナリオ1: 管理者ユーザーが新規テナントを作成してチャンネルを作成する

1. ユーザー登録画面を開く
2. 新しいテナント作成を選択する
3. ユーザー名、メールアドレス、パスワード、テナント名を入力する
4. 登録する
5. チャンネル一覧画面へ遷移する
6. チャンネル作成ボタンが表示されることを確認する
7. チャンネル名と説明を入力する
8. チャンネルを作成する
9. 作成したチャンネルが一覧に表示されることを確認する

## シナリオ2: 一般ユーザーが既存テナントに参加してメッセージを投稿する

1. ユーザー登録画面を開く
2. 既存テナントに参加を選択する
3. ユーザー名、メールアドレス、パスワード、参加コードを入力する
4. 登録する
5. チャンネル一覧画面へ遷移する
6. チャンネルを選択する
7. メッセージを入力する
8. メッセージを投稿する
9. 投稿したメッセージが一覧に表示されることを確認する
10. 投稿者名と投稿日時が表示されることを確認する
11. 別ユーザーの投稿が画面更新なしで一覧に表示されることを確認する

## シナリオ3: 一般ユーザーはチャンネルを作成できない

1. 一般ユーザーでログインする
2. チャンネル一覧画面を開く
3. チャンネル作成ボタンが表示されないことを確認する

## シナリオ4: 管理者ユーザーは参加コードを確認できる

1. 管理者ユーザーでログインする
2. テナント情報画面を開く
3. テナント名が表示されることを確認する
4. ユーザー種別が管理者として表示されることを確認する
5. 参加コードが表示されることを確認する

## シナリオ5: 一般ユーザーには参加コードを表示しない

1. 一般ユーザーでログインする
2. テナント情報画面を開く
3. テナント名が表示されることを確認する
4. ユーザー種別が一般ユーザーとして表示されることを確認する
5. 参加コードが表示されないことを確認する

## シナリオ6: ログアウトする

1. ログインする
2. ログアウトボタンを押す
3. ログイン画面へ遷移する
4. 認証後の画面にアクセスできないことを確認する

## モック方針

単体テストとコンポーネントテストでは、Firebaseとの通信は直接行わず、必要に応じてモックする。

### モック対象

- Firebase Authentication のログイン状態
- Firebase Authentication の登録処理
- Firebase Authentication のログイン処理
- Firebase Authentication のログアウト処理
- Firestore のデータ取得処理
- Firestore のリアルタイム購読処理
- Firestore のデータ登録処理
- Firestore のデータ更新処理
- 画面遷移処理

E2Eテストでは、実際の操作に近い形で確認するため、Firebase Emulator を使用する。
Firebase Authentication と Firestore を Emulator 上で動かし、テストごとに実データへ影響しない状態で主要フローを確認する。

## テストデータ方針

テストでは、以下のようなデータを使用する。

## 管理者ユーザー

```json
{
    "id": "test-admin-user",
    "displayName": "管理者ユーザー",
    "email": "admin@example.com",
    "tenantId": "test-tenant",
    "role": "admin"
}
```

## 一般ユーザー

```json
{
    "id": "test-member-user",
    "displayName": "一般ユーザー",
    "email": "member@example.com",
    "tenantId": "test-tenant",
    "role": "member"
}
```

## テナント

```json
{
    "id": "test-tenant",
    "name": "テストテナント",
    "joinCode": "TEST123",
    "createdBy": "test-admin-user"
}
```

## チャンネル

```json
{
    "id": "test-channel",
    "tenantId": "test-tenant",
    "name": "general",
    "description": "テスト用チャンネル",
    "createdBy": "test-admin-user"
}
```

## メッセージ

```json
{
    "id": "test-message",
    "tenantId": "test-tenant",
    "channelId": "test-channel",
    "body": "テストメッセージです。",
    "senderId": "test-member-user",
    "senderName": "一般ユーザー"
}
```

## テストしない対象

MVPでは、以下はテスト対象外とする。

- Firebase Authentication 自体の内部挙動
- Firestore 自体の内部挙動
- Firestore Security Rules の網羅的な検証
- ブラウザごとの細かい表示差異
- レスポンシブデザインの詳細な網羅テスト
- メール送信
- 通知
- ファイル添付
- 既読管理
- メンション
- リアクション
- スレッド返信
- メッセージ検索
- メッセージ編集
- メッセージ削除
- チャンネル編集
- チャンネル削除
- ユーザー削除
- 管理者権限の付与・剥奪
- 大量データ時のパフォーマンステスト
- 負荷テスト
- セキュリティ診断レベルの網羅テスト

## テスト実装の優先順位

MVPでは、以下の順番でテストを実装する。

1. バリデーション関数の単体テスト
2. 権限判定関数の単体テスト
3. Firestore保存用データ生成処理の単体テスト
4. ログインフォームのコンポーネントテスト
5. ユーザー登録フォームのコンポーネントテスト
6. チャンネル作成フォームのコンポーネントテスト
7. メッセージ投稿フォームのコンポーネントテスト
8. チャンネル一覧のコンポーネントテスト
9. メッセージ一覧のコンポーネントテスト
10. 管理者ユーザーのE2Eテスト
11. 一般ユーザーのE2Eテスト
12. メッセージリアルタイム表示のE2Eテスト
13. ログアウトと認証制御のE2Eテスト

## 完了条件

このテスト方針は、以下を満たす状態で完了とする。

- 使用するテストツールが明確である
- 単体テストの対象が整理されている
- コンポーネントテストの対象が整理されている
- E2Eテストの主要シナリオが整理されている
- MVPでテストする対象としない対象が明確である
- テスト実装の優先順位が明確である
- 転職用ポートフォリオとして、品質を意識していることを説明できる
